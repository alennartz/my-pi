# DR-056: The persona is persistent session config — rebind at every session boundary, announce only on override

## Status
Accepted

## Context
Persona bindings (model/thinking/tools) and persona announcements pull in opposite directions at session boundaries. Re-binding on continuation was first ruled out ("no slap-back": a resume must not stomp the user's mid-session `/model` or tool choices), then ruled back in for fresh starts and most continuations, and finally settled after live testing showed the real constraints: a continuation's fresh runtime resets the active-tool whitelist to pi's defaults, so "no rebind" silently *loses* the persona's declared capabilities; yet re-announcing on every resume spams a transcript that already carries the takeover notice. The user's framing resolved it: resume and reload are "the same thing", and fork preserves the parent's persona — one continuation case.

## Decision
The persona is persistent session config. Its front-matter bindings — `model` (tier-resolved, `:<level>` handled) via `pi.setModel`/`pi.setThinkingLevel`, `tools` via `pi.setActiveTools` — are re-applied at **every** session start: fresh starts and continuations (resume, reload, fork, CLI resume) alike. A `/model` override stands only until the session is next opened; the persona is authoritative at each boundary. Announcements happen **only on override** — a spawn-declared persona losing wholesale to the workspace persona (DR-053): the child-side override notice, once per condition via transcript dedup, plus the override note in the `subagent` tool result for the calling LLM. A persona takeover is silent by design — a workspace taking over a fresh session (root boot, `/new`, everything) announces nothing, because the directory IS the agent and `/sysprompt`'s projection is the pre-run visibility surface. `before_agent_start` never binds (mid-run boundaries stay untouched) and skills-view filtering stays per-run. Scope: root sessions; subagent children keep construction-owned binding with the persisted model surviving restore (DR-038).

Rejected: no-rebind on resume/reload (the interim rule — a continuation's fresh runtime resets tools to defaults and a stale `/model` would outlive the persona's authority, so the persona would decay with every continuation); rebind-and-re-announce (the notice's job — correcting the user's belief about who runs the session — is done once; repeats are noise); treating resume, reload, and fork as distinct cases (the user's model of the product is one continuation case; case-splitting produced two interim implementations that both had to be corrected); re-deriving a child's model on restore (DR-038 already governs: the persisted model survives, capability gates re-resolve).

## Consequences
Continuations fully re-bind and are silent. The only announcement is the override — "this session is not who you asked for" — and the calling LLM reads that in the spawn tool result, not only in the transcript. Tool-selection is not persistent pi state, so rebind-as-restore is the mechanism that keeps a whitelist alive across reload — watch for any future pi change that persists `setActiveTools` (then the rebind becomes redundant but harmless). Watch also for new session-start reasons: each must deliberately classify as continuation or takeover (DR-054's transcript-state detection, not the reason set). Costs accepted: mid-session user choices are session-scoped by design, and a takeover is invisible in-transcript by choice — `/sysprompt`'s projection (commit `5d53d6c`) carries that visibility instead.
